# 무신사 랭킹 "경량 아우터" 30분 수집기

무신사 랭킹 1~500위를 30분마다 수집해서 **상품명에 "경량"이 들어간 아우터**만 기록합니다.
기록하는 값: 순위, 가격, 보는 사람 수, 구매 수, 좋아요, 리뷰, 무배당 여부, 상세 페이지 값.

> `rank-monitor/`(일일 TOP500 슬랙 리포트), `viewer-monitor/`(코드그라피 보는인원)와는 **별개 폴더·별개 워크플로**입니다.
> 랭킹 카드 구조(data-index, data-price, 무배당발 플래그 등)는 `rank-monitor/collect_rank.js` 에서 실제로 확인된 구조를 그대로 사용합니다.

## 2. 저장 방식: 구글 스프레드시트 추천 (+ CSV 백업 자동)

| | 구글 시트 | CSV |
|---|---|---|
| 30분마다 누적 | ✅ 자동으로 아래에 쌓임 | ❌ 회차마다 파일이 따로 생김 → 매번 다운로드·병합 필요 |
| 분석 | ✅ 피벗/필터/차트 바로 가능, 팀 공유 쉬움 | 엑셀로 합쳐야 함 |
| 보관 | ✅ 영구 | GitHub Artifacts 는 30일 후 삭제 |
| 용량 | 1,000만 셀 한도 → 하루 약 1~2천 셀 예상 시 수년 사용 가능 | 제한 없음 |
| 설정 | 이 저장소에 이미 있는 `GOOGLE_SERVICE_ACCOUNT_JSON` 재사용 | 설정 없음 |

**권장: 구글 시트를 메인으로, CSV 는 매 회차 자동 백업(Artifacts)으로.**
코드는 둘 다 지원하며, 시트 Secrets 가 없으면 CSV 만 저장합니다.

시트에는 탭 2개가 자동 생성됩니다.
- `경량아우터_수집` : 데이터 누적 (1행 = 1회차 × 1상품)
- `수집로그` : 회차별 성공/실패 건수, 실패 원인, 누락 항목 통계

## 3. 설정 방법

### 3-1. GitHub Secrets (Settings → Secrets and variables → Actions)

| 이름 | 내용 |
|---|---|
| `LIGHT_OUTER_SPREADSHEET_ID` | **새로 추가**: 기록할 구글 시트 ID (URL 의 `/d/` 와 `/edit` 사이) |
| `GOOGLE_SERVICE_ACCOUNT_JSON` | viewer-monitor 에서 이미 쓰고 있는 값 그대로 사용 (추가 작업 없음) |

시트는 서비스계정 이메일(`...@...iam.gserviceaccount.com`)에 **편집자**로 공유해야 합니다.

### 3-2. (선택) Variables
| 이름 | 기본값 | 설명 |
|---|---|---|
| `MAX_DETAIL_PER_RUN` | 60 | 1회 상세 페이지 최대 수 |

### 3-3. 첫 실행 순서 (중요)
1. **Actions → 랭킹 경량아우터 30분 수집 → Run workflow → mode = `probe`**
   → Artifacts 의 `probe/` 파일로 실제 페이지 구조 확인 (스크린샷, 카드 문구, API 주소)
2. **mode = `collect`** 로 1회 수동 실행 → 로그의 "수집 요약" 과 시트 확인
3. 문제 없으면 이후 30분마다 자동 실행

### 3-4. 로컬 실행
```bash
cd light-outer-monitor
npm ci
npx playwright install chromium
npm test        # 파서 단위 테스트
npm run probe   # 구조 진단
npm start       # 수집 (시트 환경변수 없으면 output/ 에 CSV 만 저장)
```

## 4. 수집 컬럼

| 구분 | 컬럼 |
|---|---|
| 기본 | 수집키, 수집슬롯_KST(정각/30분), 수집일시_KST(실제), 랭킹순위, 순위출처, 상품코드, 상품명, 브랜드명, 브랜드코드, 상품URL, 아우터판정근거 |
| 랭킹 목록 | 목록_정상가, 목록_판매가, 목록_할인율, 목록_가격위치 (카드 data-price / data-original-price / data-discount-rate 속성) |
| 랭킹 목록 지표 | 목록_실시간보는사람수 / 목록_실시간구매중인원 / 목록_조회수 / 목록_누적구매인원 / 목록_구매건수 / 목록_리뷰수 — 각각 `값`, `_원문`, `_위치` 3칸 |
| 좋아요 | 좋아요수, 좋아요_위치 |
| 무배당 | 무배당여부, 무배당_원문, 무배당_위치, 무료배송문구, 당일출고문구 |
| 상세 | 상세_수집상태, 상세_상품코드, 상세_상품명, 상세_카테고리, 상세_소비자가, 상세_할인가, 상세_할인율, 상세_가격위치, 상세_현재보는사람수 / 조회수 / 누적구매인원 / 구매건수 / 리뷰수 / 좋아요문구 (각 값·원문·위치) |
| 점검 | 누락항목 |

### 데이터 원칙
- **화면에 보이지 않는 값은 0 이 아니라 `NULL`** (config 의 `NULL_TEXT`)
- **조회수 / 실시간 보는 사람 / 누적 구매 인원 / 구매 건수는 별도 컬럼** — 문구로 구분
  - `1.9만명이 보는 중` → 실시간보는사람수 (랭킹 카드) / `52명이 보고 있어요` → 상세_현재보는사람수
  - `1,234명이 구매 중` → 실시간구매중인원 (랭킹 카드)
  - `조회 5,600` → 조회수
  - `320명이 구매했어요` → 누적구매인원
  - `구매 1.2천+` → 구매건수 (원문에 `+` 가 남아 "이상" 표기임을 확인 가능)
- 숫자 옆 `_원문` 에 화면 문구 그대로, `_위치` 에 어디서 읽었는지(랭킹목록 카드 / 상세페이지 화면 / API응답 경로) 기록
- **무배당여부** = 랭킹 카드의 무배당발 표시 (`data-item-flag` 에 `plusdelivery` 또는 무배당 아이콘) — rank-monitor 와 같은 기준.
  카드에 이 속성이 없는 구조로 바뀌면 "무배당발" 문구로 보조 판정 (`src/parsers.js` 의 `extractDeliveryBadges`)
- **좋아요수**는 무신사 좋아요 API 값 = 상세 페이지 하트 숫자와 같은 원천 (화면은 "1.7천"처럼 축약되므로 API 사용, viewer-monitor 와 동일)
- 랭킹 카드에 "보는 중/구매 중" 문구가 아예 없는 상품은 해당 칸이 `NULL` (0으로 채우지 않음)

## 5. 동작 방식

### 목록 (1~500위)
- 페이지를 스크롤하며(무한 스크롤/동적 로딩 대응) 카드를 **누적 저장** → 화면에서 카드가 사라지는 가상 스크롤이어도 누락 없음
- "더보기" 버튼이 있으면 클릭 (페이지네이션형 대응)
- 페이지가 호출하는 내부 API(JSON) 응답도 같이 가로채서, 화면에서 못 읽은 값만 보충
- 랭킹 카드는 `[data-item-id].gtm-view-item-list` (바깥 카드)를 읽음 — 안쪽 `<a>` 는 상품명만 있어서 사용하지 않음
- **광고/추천 제외**: 카드에 `AD`/`광고`/`추천` 표시가 있거나, 순위(`data-index`)가 없는 카드(배너/추천 영역)는 제외
- **상품코드로 중복 제거**, 순위 정렬 후 500위까지만
- 순위를 어디서 정했는지 `순위출처` 에 기록 (카드 data-index 속성 / 화면 순위 숫자 / API rank / 노출 순서 추정)

### 필터 → 상세
1. 상품명에 "경량" 포함 → 후보 (500개 중 보통 수~수십 개)
2. **후보만** 상세 페이지 방문 → 카테고리 대분류 `002(아우터)` 확인
3. 카테고리를 못 읽으면 상품명 키워드(패딩/자켓/베스트 등)로 보조 판정 (`아우터판정근거` 에 "추정" 표기)

### 상세 500개를 매번 열지 않는 이유 / 대안
500개 상세를 30분마다 여는 것은 시간(약 15~25분)과 무신사 서버 부담 면에서 비현실적이라 **하지 않습니다.**
- 랭킹 500위 **목록은 매번 전체 수집** (`output/data/랭킹전체_*.csv` 로도 저장)
- 상세는 **"경량" 후보만** 방문
- 후보가 `MAX_DETAIL_PER_RUN`(60) 을 넘으면 순위순으로 묶음을 나눠 **회차마다 돌아가며** 수집
  (이번 회차에 빠진 상품은 `상세_수집상태 = 이번 회차 상세 미대상(순환 수집)` 로 기록, 목록 값은 정상 기록)

### 오류 처리
| 상황 | 처리 |
|---|---|
| 네트워크 오류/타임아웃 | 3초 → 6초 대기 후 최대 2회 재시도 |
| 상세 404 (판매종료) | 재시도 없이 실패 기록 |
| 일부 상품 실패 | 해당 상품만 `상세_수집상태 = 실패: 원인`, 나머지는 정상 저장 |
| 실행 시간 초과 (20분) | 남은 상세 수집 건너뛰고 지금까지 결과 저장 |
| 같은 슬롯 재실행 | 시트에 같은 `수집키(슬롯|상품코드)` 가 있으면 저장 안 함 |
| 동시 실행 | 워크플로 `concurrency` 로 1개씩만 실행 (뒤 실행은 대기) |
| 목록 0건 | 워크플로를 실패(빨간불) 처리 → GitHub 알림 메일 |

### 로그
- Actions 실행 화면 **Summary** 에 요약 표 (성공/실패/누락 + 수집 상품 목록)
- 시트 `수집로그` 탭, `output/logs/수집로그_*.json` (실패 상품별 원인 포함)
- **누락항목** 컬럼: 필수 값이 NULL 인 항목 이름 → 오류 수정 포인트

## 6. 값이 NULL 로 나올 때 (수정 가이드)

1. `mode = probe` 로 실행 → Artifacts 다운로드
2. `probe/ranking_cards.json` 에서 카드 문구 확인
   - 문구가 바뀌었으면 → `src/parsers.js` 의 `METRIC_RULES` 정규식 수정
3. `probe/ranking_api_samples.json` 에서 필드 이름 확인
   - 필드 이름이 바뀌었으면 → `src/jsonGoods.js` 의 `KEY_ALIASES` 에 추가
4. `probe/detail_*.json` 에서 상세 페이지 문구/카테고리 확인
5. 수정 후 `npm test` 로 기존 규칙이 깨지지 않았는지 확인

## 7. 실행 시간
- 목록 500위 스크롤: 약 2~5분 / 상세 1개: 약 5~8초 (동시 2개)
- 후보 60개 기준 예상 총 8~12분 → 30분 주기 내 실행 가능
- 하드 제한: 실행 예산 20분(`RUN_BUDGET_MINUTES`), 워크플로 28분(`timeout-minutes`)
